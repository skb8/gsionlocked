# iQOO Neo10 CN / PD2425: диагностический порт

## Результат

Это основа порта для PD2425 / SM8650 / Android 16 / OriginOS 6 с уже
полученным временным root GhostLock + KernelSU LKM. **Полная загрузка Android
на Vivo не реализована и не проверена.** В 0.1.11 добавлен отдельный ограниченный
запуск linker/shell из настоящего GSI, ещё не проверенный на устройстве. APK и
native preflight не являются установщиком полного runtime. Совпадение OTA не
включает полный запуск.

В APK добавлены определение PD2425 и диагностика device/model/API/ABI/fingerprint
без root. Start завершается отказом до подготовки launcher и запуска root-сессии.
В Samsung loader/guardian добавлена безусловная ранняя проверка model/device/API/
bootloader, независимо от TEMPGSI_HAL_PROFILE151. Проверка добавлена и в
EvoxWork198 до файловых операций и SELinux lease. Существующие проверки образа,
хешей, prepared profile и изоляции сохранены.

PD2425 loader/guardian сейчас являются **только диагностическими программами**.
Они принимают --check-host, --diagnose, --diagnose-json и отдельные --test-cgroup / --test-isolation / --test-bootstrap; остальные операции запрещены.
Профиль содержит launch_enabled=false. Проприетарные файлы Vivo в Git не включены.

## Init, HAL, VINTF и SELinux

| Подсистема | Данные OTA | Препятствие |
| --- | --- | --- |
| Дисплей | vendor.qti.hardware.display.composer; Composer3 AIDL v2 | Нужны ownership, приватный Binder и точное восстановление |
| Аудио | vendor.audio-hal; HIDL audio 7.1/effect 7.0 | Иной бинарник и граф restart; Samsung sec-audio неприменим |
| Power/Lights/Health | vendor.power / vendor.qti.light / vendor.health-default | Иные пути и контракты процессов |
| Камера | vendor.camera-provider, QTI/Vivo интерфейсы | Samsung provider и shims неприменимы |
| Отпечаток | biometrics-fingerprint; IFingerprint AIDL v3 | Домен vivo_hal_fingerprint и иной адаптер |
| Gatekeeper | Объявлены QTI default и SPU варианты | Активный вариант нужно определить на устройстве |
| Температура | thermal-engine и vendor.thermal-hal | OEM thermal mitigation должна работать |

QTI composer имеет onrestart restart surfaceflinger; SurfaceFlinger перезапускает
работающий zygote. Audioserver перезапускает несколько audio HAL, а vendor
HAL перезапускает audioserver. У zygote есть действия рестарта других служб
и vivo.zygote_restart; найден zygote_third. Остановка двух Samsung zygote не
является проверенным протоколом quiesce для OriginOS.

Основной manifest, manifest_pineapple.xml, manifest_cliffs.xml и fragments
не следует механически объединять в активную конфигурацию. Профиль сохраняет
офлайн-декларации, а не инструкции по остановке служб.

Найдены goodix_ts.ko, включая каталог 6.1-gki, и VTS paths /sys/class/vts/vivo_ts
и /sys/touchscreen. Семантика записи для передачи дисплея/ввода не доказана.
Samsung запись `2,1`/`1,0` в /sys/class/sec/tsp/enabled на Vivo не добавлена.

Composer file label — hal_graphics_composer_default_exec; fingerprint —
vivo_hal_fingerprint_exec. File label не доказывает фактические credentials,
transition и effective SELinux allow. Совместная работа system 36 и vendor
policy 34.0 требует проверки полного policy/mapping, а не копирования Samsung
groups/capabilities/identities.

Исходный EvoxWork198 вызывает setenforce 0 и пытается вернуть исходный режим.
Enforcement общий для ядра, mount namespace его не изолирует. Автоматическое
отключение SELinux для PD2425 не включено. Enforcing-совместимость и надёжное
восстановление ещё не реализованы.

Samsung guardian требует watchdog fd у system_server с identity Software Watchdog,
timeout 100, KEEPALIVE и MAGICCLOSE. OTA не устанавливает живого владельца fd,
armed-state или доступность pidfd_getfd. PD2425 preflight не открывает watchdog.

## Установка и диагностика

APK versionCode 209, versionName 0.1.12-pd2425-loop-discovery. Debug APK подписан
тестовым ключом, без опционального встроенного KernelSU APK. Разные CI-сборки
могут иметь разные debug-ключи. Обновление поверх приложения с иной подписью
не сработает; удаление приложения удаляет его импортированные файлы.

```
adb install gsionlocked.apk
```

На PD2425 откройте «Диагностика PD2425». Root для неё не требуется. Check root
использует существующий backend приложения; uid=0 не доказывает версию/тип root
или возможность handoff. Root нужно получить и разрешить отдельно.

Расширенный read-only отчёт:
```
python tools/diagnose_pd2425.py --output pd2425-diagnostics.json
python tools/diagnose_pd2425.py --root --output pd2425-root-diagnostics.json
```

--root использует уже авторизованный su. Скрипт читает ограниченные properties,
состояния служб, имена input, watchdog metadata, cgroup, uname, SELinux; с root —
modules и хеш живой policy. Ошибки чтения сохраняются. Serial из --serial не
записывается. Код 4 означает совпадение OTA при неготовом runtime; 2 — несовпадение.

Native-проверка:
```
adb push guardian-pd2425-preflight /data/local/tmp/
adb shell chmod 755 /data/local/tmp/guardian-pd2425-preflight
adb shell /data/local/tmp/guardian-pd2425-preflight --diagnose
```

Push/chmod создают только диагностический файл на userdata. Программа не меняет
службы, SELinux или mounts. Для --check-host/--diagnose код 0 означает совпадение точного профиля хоста; 31 — mismatch;
78 — запрещённую операцию. Всегда выводится runtime_ready=0. Loader preflight
имеет тот же контракт. Это не штатные loader/guardian запуска GSI.

Не устанавливайте Samsung prepared profile, work198.jar, shims или чужие
calibration/biometric данные на Vivo. Для этой версии не нужны fastboot flash,
запись в block devices, изменение vbmeta/boot/init_boot/vendor_boot/super.

## Сборка и проверки

Linux x86_64, JDK 17, SDK platform 35/build-tools 35.0.0, NDK 25.2.9519653:
```
python tools/audit_public.py
python tools/test.py
python tools/test_pd2425.py
python tools/test_live_probe.py
python tools/test_profile_review.py
python tools/test_cgroup_probe.py
python tools/test_namespace_probe.py
python tools/test_bootstrap_probe.py
python tools/test_syscall_guard.py
python tools/test_gsi_preview.py
python tools/build_app.py --debug
python tools/build_runtime.py --sdk "$ANDROID_HOME" --java-home "$JAVA_HOME"
```

Задайте ANDROID_HOME, JAVA_HOME, при необходимости ANDROID_NDK_HOME.
Runtime build.json содержит SHA-256 и статус компонентов. Собираются
Samsung loader/guardian и dex jar для ревью, PD2425 preflight,
artd-session.so, private-selinux-mount.so, property seeder, soft-keymint-service
и два Android native test binary. Это не полный установочный комплект.
Soft KeyMint требует внешней реализации и соответствующего ABI.

Локально после восстановления пройдены C identity/CLI/gate tests, проверка
multiline init/VINTF parser, Python syntax и audit_public. Java/APK/native Android
сборку текущего состояния проверяет CI. Native storage/UID тесты лишь собираются;
исполнение требует целевого Android ядра/root и здесь не заявлено.

Для повторного извлечения OTA:
```
payload-dumper-go -p vendor,odm,product,system_ext,vendor_dlkm,vendor_boot,init_boot,system -o images ota.zip
fsck.erofs --extract=fs/vendor --no-preserve images/vendor.img
fsck.erofs --extract=fs/odm --no-preserve images/odm.img
fsck.erofs --extract=fs/product --no-preserve images/product.img
fsck.erofs --extract=fs/system_ext --no-preserve images/system_ext.img
fsck.erofs --extract=fs/vendor_dlkm --no-preserve images/vendor_dlkm.img
fsck.erofs --extract images/system.img
dump.erofs --cat --path=/system/build.prop images/system.img
```

Сохраните выбранные system init/SELinux/VINTF files в system-selected:
```
python tools/analyze_pd2425.py --tree fs --system-selected system-selected --output inventory.json
```

Анализатор не выбирает активные imports/VINTF variants и не вычисляет effective
SELinux policy или ABI-совместимость. Образы/распаковку держите вне репозитория;
для полной распаковки нужно значительно больше диска, чем размер ZIP.

## Следующий этап: live probe (0.1.4)

Предыдущий Actions run для c80bc6d успешно собрал APK, весь публичный runtime
и выполнил тесты. Это доказательство сборки, а не возможности takeover на Vivo.

В 0.1.4 добавлен native JSON probe, включённый в APK как arm64 executable в
nativeLibraryDir. Он запускается через существующий KernelSU/su backend по
кнопке **«Root-отчёт PD2425»**. Root нужно разрешить отдельно. Запуск бинарника
на самом PD2425 ещё требует проверки; отказ SELinux/KernelSU будет показан как
ошибка, без попытки обхода.

Отчёт фиксирует:

- Версию ядра, enforcement, battery temp и cgroup v2 controllers с errno чтения.
- Состояния init-служб и init.svc_debug_pid. Для процесса читаются exe, starttime,
  Uid/Gid/Groups/CapEff и SELinux context. Эти данные повторно сверяются в конце
  чтения: смена PID/starttime, credentials, exe/context или состояния init
  делает snapshot_stable=false. Это ограниченное наблюдение, а не замораживание
  процесса или проверка его доверенности.
- Если init PID property недоступна, уникальный среди видимых процессов match
  executable фиксируется только как pid_source=exe_candidate. Это не доказанный
  владелец init-службы. Несколько совпадений остаются неоднозначными; ошибки и
  ограничения сканирования сохраняются.
- Возможности KEY_VOLUMEUP/KEY_VOLUMEDOWN/BTN_TOUCH через read-only EVIOCG*
  запросы. События клавиш и касаний не читаются, EVIOCGRAB не используется.
- Метаданные watchdog0 и ссылки на watchdog fd в system_server. Устройство
  /dev/watchdog не открывается, fd не дублируется, KEEPALIVE/options не меняются.
  fd_adoption_tested=false остаётся обязательным ограничением.

Список наблюдаемых служб генерируется из профиля при сборке APK/runtime,
включая zygote_third, framework и thermal-службы. Это не список для ctl.stop.
Режим --diagnose-json не содержит service control, mount, setenforce или записи в sysfs. Отдельный --test-cgroup описан ниже и создаёт временную cgroup только для своих процессов.

После успешного сбора нажмите **«Сохранить root-отчёт»** и выберите файл JSON.
Отчёт не отправляется автоматически. Он содержит технические PID/UID/контексты,
а не serial, calibration, биометрию или содержимое пользовательских файлов.
Открытие приложения с root само по себе не включает запуск GSI.

При работе через ADB можно использовать runtime binary:
```
adb shell su -c '/data/local/tmp/guardian-pd2425-preflight --diagnose-json' > pd2425-live-report.json
python tools/review_pd2425.py pd2425-live-report.json --output pd2425-review.json
```

Native mismatch возвращает 31, сохраняя JSON. В APK такой отчёт можно сохранить
для разбора несовпадения; это не отключает launch gate. Native schema-2 JSON и
старый отчёт diagnose_pd2425.py имеют разные схемы: review_pd2425.py принимает
только native schema 2.

Review проверяет исходные поля identity самостоятельно, root UID, enforcing,
температуру, metadata/errors, наблюдения процессов и возвратные key capabilities.
Даже observation_checks_passed=true оставляет runtime_ready=false. Проверка не
генерирует runtime authorization или команды изменения служб. PID-кандидаты
не считаются подтверждённым init PID. Список необходимых физических проверок
остаётся в каждом review.

Тест test_live_probe.py использует вымышленные proc/sys/dev данные. Проверены
PID/state races, статический starttime parser с пробелами/скобками в comm,
недоступные contexts, несколько executable candidates, JSON escaping и ошибки
input ioctl. Тест перехватывает open/ioctl: write opens, открытие watchdog и
setter ioctl приводят к отказу теста. Это проверяет код probe, а не прошивку Vivo.

Для следующего этапа адаптации нужен именно live JSON с реального телефона.
Без него нельзя обоснованно выбрать HAL identities, service ownership,
watchdog recovery и протокол quiesce. После отчёта всё равно потребуются
ограниченные физические тесты и полный bootstrap выбранного GSI.


## Данные владельца и этап изоляции (0.1.5)

Владелец предоставил schema-2 JSON, собранный предыдущим APK на телефоне.
Исходный отчёт с PID/starttime в Git не добавлен. В профиле сохранены только
производные аппаратные/служебные факты и SHA-256 источника.

Подтверждено в этом наблюдении: UID 0, SELinux Enforcing, API 36 / arm64-v8a,
ядро 6.1.145-android14-11-maybe-dirty, температура 27,8 C и стабильные snapshots
14 работающих служб. Это не подтверждает тип root, пригодность гостя,
работу HAL после takeover или возможность восстановления после сбоя.

### Fingerprint и идентичности

Фактический fingerprint содержит точный build ID `BP2A.250605.031.A3_V000L1`,
а metadata OTA — `BP2A.250605.031.A3`. Компилятор и device совпадают.
Добавлен ровно один наблюдавшийся полный fingerprint; произвольные суффиксы,
другие сборки/API/ABI не разрешаются. `ota_identity_match` по-прежнему означает
точное совпадение исходного OTA fingerprint. Отдельный `host_profile_match`
учитывает два явно перечисленных значения. Launch gate остаётся закрыт.

Observed identity хранит UID, **отдельный первичный GID**, точное множество
supplementary groups, CapEff и SELinux context. Например, у Composer UID 1000,
GID 1003, supplementary group 1026. Подмена GID значением UID или добавление
primary GID в supplementary groups не считается совпадением.
Native probe сверяет эти данные; reviewer независимо проверяет drift.
Эти таблицы не применяют credentials и не запускают vendor binaries.

В отчёте активен vendor.gatekeeper_default с контекстом
vendor_hal_gatekeeper_qti. У SPU-варианта нет init property. Это зафиксировано
как наблюдавшийся выбор альтернативы, а не как доказательство отсутствия
бинарника. Неактивная SPU-служба не требуется, пока ожидаемая default-служба
работает стабильно; её исчезновение или активация SPU требуют разбора.
Контекст vendor_thermal-engine с дефисом обрабатывается без ложного отказа.

### Физические кнопки

Возвратные устройства выбираются по profile-named источникам и capabilities:
`gpio-keys` с Volume Up и `pmic_resin` с Volume Down. Event numbers не закреплены.
Гарнитура, также объявляющая обе клавиши, исключается. Дубликаты, ошибки ioctl
и неоднозначные источники не проходят проверку. Фактическое удержание комбинации
и возврат из гостевой сессии всё ещё не проверялись.

### Cgroup

Пустой cgroup.controllers не означает, что cgroup2 или cgroup.kill отсутствуют:
controllers описывают управление ресурсами, а не доказывают доступность kill.
См. [документацию ядра](https://docs.kernel.org/admin-guide/cgroup-v2.html).
По исходному отчёту версия FS и cgroup.kill оставались непроверенными.
Новый read-only JSON фиксирует statfs, self cgroup, boot ID и root context.

В APK есть отдельная кнопка **«Root-отчёт + тест cgroup»**. Она сначала собирает
read-only snapshot, затем только при точном профиле хоста запускает тест.
Тест требует UID 0 и Enforcing, проверяет тип cgroup2 у /sys/fs/cgroup,
создаёт новую уникальную группу mode 0700 и два собственных дочерних процесса.
Родитель и процессы OriginOS в неё не переносятся. cgroup.subtree_control,
ресурсные лимиты, mounts и SELinux не меняются.

Перед cgroup.kill проверяются pidfd обоих детей, точный список участников
и populated=1. После записи проверяются завершение обоих, populated=0,
reap и удаление группы. При ошибке group-kill не используется как cleanup:
убиваются только созданные тестом, ещё не reaped дочерние PID. В отдельном
процессе теста SIGCHLD временно переводится в default, чтобы IDs не могли
переиспользоваться до waitpid; старое disposition возвращается. Не переносите
этот core в многопоточный процесс с чужим reaper без отдельного дизайна.

У детей установлен parent-death SIGKILL; проверяется race с выходом родителя.
Внешний таймер probe — 12 секунд. При аварийном прерывании может остаться пустая
временная группа: это не выдаётся за успешную очистку. Путь созданной группы,
stage, errno, cleanup_errno и cleanup_complete включены в JSON.
Не пытайтесь вручную удалять чужие или населённые cgroup.

Для отдельного native-запуска:
```
adb shell su -c '/data/local/tmp/guardian-pd2425-preflight --test-cgroup'
```

0 означает успех child-only теста, 40 — отказ/ошибку теста, 31 — host mismatch.
Успешный тест всегда оставляет runtime_ready=false и не проверяет гостевой
namespace, FUSE/Binder, дисплей или восстановление хоста.

Комбинированный JSON имеет schema 3 и no_device_changes=false: временная группа
и дочерние процессы действительно создавались или могли создаваться. При этом
observations_read_only=true относится к исходному snapshot; тест записан в
self_tests.cgroup. Reviewer связывает его с snapshot по точному fingerprint и
boot ID и проверяет все результаты, включая cleanup. Одного passed=true мало.
Никаких данных автоматически не отправляется. Сохраните JSON прежней кнопкой.

## Подтверждение cgroup и BinderFS-проба (0.1.6)

Во втором отчёте владельца тест 0.1.5 **успешен**: UID 0, u:r:ksu:s0,
Enforcing, cgroup2, два собственных процесса, два pidfd, точное membership,

## BinderFS с начальными узлами (0.1.7)

Отчёт 0.1.6 подтвердил два разных mount/network namespace, MS_PRIVATE, tmpfs,
mount BinderFS и открытие private binder-control. В обоих детях первая
BINDER_CTL_ADD вернула errno 17 (EEXIST), до проверки Binder protocol. Поэтому
passed=false корректен. Ветка ошибки завершила обоих детей и удалила временные
каталоги/cgroup без ошибок; cgroup.kill в этой попытке не вызывался.
parent_checked=false означает, что проверка родителя тогда не выполнялась,
а не доказательство повреждения OriginOS. Предыдущий успех отдельного cgroup
теста сохранён как отдельное доказательство, но не переносится на этот тест.

Причина, согласующаяся с отчётом: начальные Binder-узлы могут создаваться самим
ядром при mount из binder_devices_param. Это поведение есть в
[Android common kernel binderfs_fill_super](https://android.googlesource.com/kernel/common/+/ef852baaf6a73551cfaa0d082477b50d842b79b8/drivers/android/binderfs.c).
Точный параметр живого ядра этим отчётом ещё не установлен.
Проба 0.1.6 ошибочно предполагала отсутствие стандартных узлов в новой BinderFS.

В 0.1.7 сначала проверяется тип FS через FD private binder-control
(BINDERFS_SUPER_MAGIC). Для каждого стандартного имени lstat отличает уже
созданный ядром узел от отсутствующего: только отсутствующий создаётся ioctl.
Проверяются char-device, тот же st_dev, что у control, отличие major/minor от
всех stock-узлов/второго ребёнка, отсутствие дубликатов и Binder protocol 8.
У созданного ioctl узла проверяются возвращённые major/minor. После open с
O_NOFOLLOW проверяются st_dev/inode/rdev открытого FD против lstat. Symlink,
другая FS, подмена inode, несовместимый protocol и неожиданный EEXIST от ioctl
по-прежнему приводят к отказу. Узлы хоста не используются и не удаляются.

JSON добавляет binderfs_verified и allocation (mount-created/ioctl-created/
unverified). Историческое devices_created — число успешно проверенных узлов,
включая созданные ядром при mount. Родитель теперь проверяется после получения
обоих отчётов даже при ошибке ребёнка; прошедший тест требует всех прежних
условий, сохранности родителя и полной очистки. Reviewer требует новый признак
проверенной BinderFS, один passed по-прежнему недостаточен.

CI воспроизводит пустую BinderFS, все восемь сочетаний предсозданных трёх узлов,
EEXIST при неожиданной гонке, symlink, чужую FS, подмену FD и ошибки ioctl.
Успех на телефоне ещё не получен. Повторите «Тест namespaces/BinderFS» на 0.1.7
и сохраните JSON; GSI launch остаётся закрытым.

## Инертный каркас PID/proc/rootfs (0.1.8)

В исходном runtime приватные mounts/proc, корневая FS, APEX, свойства и служебные
процессы связаны с большим набором device-specific условий. Подтверждённые root
и BinderFS не разрешают копирование всей последовательности Samsung на Vivo.
Следующий реализованный этап — **только доверенный инертный каркас**, не Android
init и не выполнение пользовательского GSI. Его состояние — device-unvalidated.

Отдельная кнопка **«Тест PID/proc/rootfs»** вызывает `--test-bootstrap` и сохраняет
`self_tests.bootstrap`. Точные проверки хоста, UID 0, Enforcing и cgroup2 сохранены.
Guardian-процесс создаёт ровно двух непосредственных детей с CLONE_NEWPID:
каждый является PID 1 в собственном PID namespace, без дополнительных внуков.
До подтверждения pidfd, точного membership и populated=1 дети ждут gate.

На Android применяется Bionic clone(NULL,NULL,flags,NULL), поддерживающий fork-like
вызов и обновление cached pid/tid. Raw clone на Android не применяется: обход
Bionic оставил бы неверное состояние libc. Проверка parent-death race использует
унаследованный pidfd родителя, поскольку getppid внутри нового PID namespace
равен 0. PR_SET_PDEATHSIG=SIGKILL устанавливается до проверки pidfd и gate.
Описание Bionic: [clone.cpp](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/bionic/clone.cpp).

В каждом ребёнке создаётся отдельный mount namespace и MS_REC|MS_PRIVATE,
своя tmpfs 1 MiB и собственный procfs. Proc монтируется именно новым PID 1:
унаследованный proc хоста для гостя не подходит. Tmpfs и proc монтируются/
переводятся в read-only, nosuid, nodev, noexec. Перед chroot закрываются **все**
унаследованные FD через close_range, кроме write-end канала результата.
При отсутствии close_range тест отказывает без обхода этого условия.
Затем chroot/chdir переводят ребёнка в пустой rootfs.

Проверяются PID=1, PPID=0, /proc/self=1, ровно один числовой PID в proc,
тип и read-only flags обеих FS, разные PID/mount namespace ID и разные root FS
между детьми/родителем. /system, /vendor, /data, /sys и /dev должны отсутствовать.
Стандартные потоки закрыты; результат идёт только в унаследованный pipe.
Никакие программы, shell, APEX, HAL или init внутри не запускаются.

Родитель проверяет свои PID/mount/network namespace, корень, stock Binder и
parent-visible каталоги. **Перед cgroup.kill состав группы проверяется повторно**,
в том числе после длительной работы ребёнка. Появление чужого участника или
выход ребёнка запрещают group kill: cleanup касается только собственных ещё
не reaped PID. После штатного kill проверяются drain, reap двух непосредственных
детей и удаление временных ресурсов. Внешний deadline — 25 секунд, APK ждёт
probe до 45 секунд. При аварийном завершении могут остаться собственные пустые
каталоги/группа; это не выдаётся за успешную очистку.

Ограничение принципиальное: root-only доверенный C-код всё ещё не является
sandbox для произвольного кода. Chroot/read-only proc не доказывают защиту
глобальных syscalls, BPF, SELinux, полной Android FS, оборудования или данных
хоста. Профиль хранит scaffold отдельно от validated_components; до отчёта с
телефона он не подтверждён. Даже успешный self-test оставляет launch_enabled=false.

Установите APK 0.1.8, в OriginOS запустите «Тест PID/proc/rootfs», разрешите root,
затем сохраните root-отчёт. Старую BinderFS-пробу повторять не требуется.
Для native-запуска:
```
adb shell su -c '/data/local/tmp/guardian-pd2425-preflight --test-bootstrap'
```
Коды: 0 — успех этой пробы, 31 — несовместимый host, 40 — ошибка теста.
Reviewer связывает bootstrap с исходным snapshot по fingerprint/boot ID,
проверяет private PID1/proc/rootfs, flags/FD closure, родителя и cleanup.
Он не переносит успех этой пробы на Binder/network или полноценную GSI.

CI подставляет clone-related worker syscalls/mount/chroot/FD closure; реальные
namespace/rootfs на runner не создаются. Негативные сценарии охватывают PID не 1,
общий namespace/root, неправильный proc, writable FS, унаследованные FD, утечки
host paths/PID и частичные ошибки. Cgroup core отдельно проверяется на настоящих
собственных процессах с подставной cgroup FS, включая позднего чужого участника.
Android-сборка проверяет Bionic API; фактическая работа PID namespace/close_range
требует результата с устройства.


## Отказ PID namespace и отдельный rootfs-каркас (0.1.9)

Отчёт 0.1.8 остановился на create/errno=2, parent_pid_namespace/root равны нулю,
cgroup не создавалась и детей не было. Порядок операций pd_boot_create показывает,
что не прошёл первый stat /proc/self/ns/pid. Это **не** отказ clone, chroot, proc
или cleanup: до них выполнение не дошло. Проверка родителя не выполнялась;
parent_unchanged=false здесь не доказывает изменение OriginOS.

Отсутствие PID namespace entry согласуется с CONFIG_PID_NS=n: Linux добавляет
pid/pid_for_children в proc namespace inventory условно по этой опции.
[Исходник Linux/Android](https://android.googlesource.com/kernel/common/+/1b940dd55d42/fs/proc/namespaces.c).
Но конфигурация именно Vivo-ядра этим JSON не прочитана, поэтому это гипотеза,
а не установленный факт. Новый read-only snapshot перечисляет доступность
mnt/net/pid/pid_for_children/ipc/uts/user/cgroup с errno без попытки их создать.

Уточнение архитектуры: исходный loader198.c сам не вызывает CLONE_NEWPID и
использует общий PID namespace; для защиты применяет отдельные signal/BPF/
seccomp-ограничения, private mounts и cgroup. Настоящий PID1-тест 0.1.8 был
дополнительным более строгим экспериментом, а не обязательным требованием
оригинального проекта. Предыдущие формулировки о необходимости PID 1 для
оригинала следует читать с этим уточнением. Возврат к shared-PID архитектуре
требует полноценной проверки ограничений, а не снятия launch gate.

`--test-bootstrap` сохранён строгим: отсутствие PID entry остаётся отказом,
теперь stage=parent_pid_namespace. Автоматического fallback нет. Добавлен другой
компонент `--test-rootfs` / `rootfs-self-test`, кнопка **«Тест rootfs без proc»**.
Он работает только с двумя собственными обычными дочерними процессами, приватным
mount namespace, пустой tmpfs 1 MiB, read-only/nosuid/nodev/noexec, close_range
и chroot/chdir. /proc вообще не создаётся и должен отсутствовать внутри rootfs;
/system, /vendor, /data, /sys и /dev также отсутствуют. Host PID namespace остаётся
общим; Android/GSI/shell или произвольный код внутри не исполняются.

Проверяются независимые mount/root identities, read-only FS, закрытие всех FD
кроме write-end отчёта, сохранность проверяемых parent root/mount/net/Binder,
точный состав cgroup перед стартом и повторно перед kill, drain/reap/cleanup.
Отсутствующий PID namespace не мешает этому ограниченному тесту, но успех
не означает PID/proc/Binder isolation и не разрешает выполнение GSI.
Deadline, root/Enforcing/host gates и правила cleanup те же, что в 0.1.8.

JSON хранит результат отдельно в self_tests.rootfs, указывает
pid_namespace_required=false и proc_required=false. Неиспользуемые PID namespace
поля нулевые, proc_self_pid/proc_pid_count=0, proc_read_only=false. Reviewer
проверяет именно этот контракт и возвращает rootfs_test_passed отдельно;
bootstrap_test_passed не становится true. Проверки не подменяются фиктивным PID 1.

Для устройства нужна только новая проба «Тест rootfs без proc» на APK 0.1.9,
затем сохранение JSON. Строгую PID-пробу повторять сейчас не нужно. Её отказ
не доказывает невозможность исходной shared-PID архитектуры, но полноценный
порт по-прежнему ограничен sandbox/seccomp/BPF, SELinux, HAL/bootstrap и
восстановлением watchdog/display/touch. Проприетарных файлов и raw отчёта в Git нет.


## Подтверждение rootfs и ограниченный syscall guard (0.1.10)

Отчёт владельца 0.1.9 прошёл rootfs-self-test: два обычных непосредственных
ребёнка, разные mount namespace/root FS, read-only tmpfs, закрытие унаследованных
FD, сохранность проверенных parent properties и cgroup.kill/drain/reap/cleanup
без ошибок. /proc не монтировался, PID namespace общий. Санитизированные факты
и SHA-256 сохранены в validated_components.rootfs_only. Этот тест повторять
отдельно не требуется. Namespace inventory показал mnt/net/uts/cgroup доступными,
pid/pid_for_children/ipc/user — отсутствующими с ENOENT. Это наблюдения proc,
не извлечённая конфигурация ядра.

Следующий отдельный компонент — `--test-guard`, кнопка **«Тест syscall guard»**.
Используется уже проверенный rootfs-only каркас. После setup, закрытия FD и
chroot каждый собственный ребёнок устанавливает no_new_privs=1 и seccomp filter
только для себя. Родитель не устанавливает этот фильтр и сохраняет возможности
завершения собственных детей. До и после их работы сравниваются parent seccomp
mode и no_new_privs; проверяется, что signal=0 на себя у родителя разрешён.

Фильтр проверяет ABI arch и возвращает EPERM для 12 syscall-путей:
kill, tkill, tgkill, pidfd_send_signal, rt_sigqueueinfo, rt_tgsigqueueinfo,
ptrace, process_vm_writev, process_madvise, bpf, perf_event_open, process_vm_readv.
Для неправильного ABI — KILL_PROCESS; host x86_64 тест также отклоняет x32
syscall numbers, использующие тот же audit arch. На Android целевой ABI arm64.
Основа — signal/BPF filters оригинального loader198, но здесь объединённая
ограничительная экспериментальная политика, а не готовая политика для всех
Android-служб. В частности, blanket tgkill denial нельзя без проверки перенести
на Java/zygote. Запуск служб по-прежнему закрыт.

Перед установкой child проверяет разрешённый self signal=0; после установки
проверяются PR_GET_NO_NEW_PRIVS=1, SECCOMP_MODE_FILTER=2 и все 12 EPERM.
Диагностические вызовы безопасны и без фильтра: только signal=0 на самого себя,
нулевая длина remote-memory I/O на себя либо недопустимые fd/request/attribute.
Настоящие сигналы службам, ptrace attach, чтение/запись чужой памяти, perf events
и загрузка BPF-программ не выполняются. Если baseline или установка/проверка
не прошли, тест отказывает и guardian завершает только собственных детей.

Результат хранится в self_tests.guard с guard_required=true и отдельными
результатами denial по именам syscall. Reviewer требует все 12 имён без повторов,
EPERM, проверенный rootfs/parent/cleanup и исходные exact host/root/Enforcing.
Успех даёт syscall_guard_test_passed и rootfs_test_passed; PID/proc/Binder/GSI
readiness не подтверждаются. Профиль пока хранит guard как device-unvalidated.

Локальный тест и CI устанавливают реальный seccomp в отдельном собственном
дочернем процессе без root. Проверяются все отказы, допустимый write, policy
решения для неправильного arch/x32, сохранность seccomp/no_new_privs родителя.
На CI rootfs/chroot/mount по-прежнему подставные; Android arm64 API проверяет
сборка, а телефонная интеграция требует нового JSON.

Важно для дальнейшего порта: seccomp сам по себе не полный sandbox, что прямо
оговорено в [документации ядра](https://docs.kernel.org/userspace-api/seccomp_filter.html).
Этот короткий deny list не покрывает остальные глобальные syscalls, все
возможности root, IPC, сетевую/SELinux изоляцию, HAL и оборудование. Произвольный
код GSI не запускается; launch_enabled=false сохранён. Никаких разделов не
прошивается и глобальная политика SELinux не меняется.

Установите APK 0.1.10, запустите только «Тест syscall guard», разрешите root и
сохраните JSON. Проба использует два собственных ребёнка, deadline 25 секунд;
старые BinderFS/PID/rootfs тесты повторять отдельно не требуется.


## Настоящий GSI: headless linker/shell preview (0.1.11)

Владелец разрешил восстановление перезагрузкой и отложил быстрое переключение
назад. Для PD2425 hot restore больше не цель первого физического запуска.
Существующий Samsung guardian не изменён. Проверки защиты исходных разделов,
профиля и источников сохранены. Headless preview вообще не останавливает службы
OriginOS и не захватывает оборудование; после него штатно завершается только
собственный процесс. Автоматической перезагрузки в этом режиме нет.
Перезагрузка освобождает временные kernel mounts, но не откатывает записи в
файлы: поэтому GSI и runtime здесь неизменно read-only, записи в userdata нет
(кроме явно импортируемой копии образа в собственных данных APK).

Guard self-test 0.1.10 подтверждён последним отчётом владельца: оба ребёнка
проверили 12 EPERM, no_new_privs=1, seccomp mode 2; parent mode/no_new_privs
остались исходными, cleanup без ошибок. В Git внесены только санитизированные
факты и SHA-256 отчёта.

### Что выполняется

Кнопка **«Запустить linker/sh из GSI»** вызывает отдельный native компонент
libpd2425_gsi.so. Прежний Start остаётся закрытым для полной Android-сессии.
Требуются точный host fingerprint/API/ABI, UID 0, Enforcing, температура <=38 C
и точный размер/SHA-256 образа. SHA пересчитывается native-кодом по открытому
O_RDONLY FD, до любого mount; сравниваются metadata файла до/после чтения.
Не принимаются block devices, sparse/другие images и symlink к исходному файлу.

Guardian создаёт одного собственного ребёнка, pidfd и parent-death protection.
В ребёнке unshare mount/network и MS_REC|MS_PRIVATE подтверждаются разными
namespace identities. Образ подключается через LOOP_CONFIGURE с READ_ONLY и
AUTOCLEAR, монтируется ext4 с MS_RDONLY|MS_NOSUID|MS_NODEV и noload (без journal
replay). Существующий занятый loop не отсоединяется. Допускаются только loop
block devices major 7 с ожидаемым minor; raw разделы не используются.

Runtime APEX открывается через openat2 IN_ROOT/NO_MAGICLINKS внутри GSI; его
размер/полный SHA проверяются отдельно. Точный pinned payload монтируется вторым
read-only/autoclear loop. /apex внутри private namespace — собственная tmpfs;
привилегированные mount targets открываются с NO_SYMLINKS, поэтому абсолютные
symlink из GSI не направляют mount в host tree. Linker/sh проходят ELF64/AArch64
проверку; SUID/SGID и file capabilities на исполняемом linker запрещены.
Host /data, /dev, /sys, /proc и HAL не bind-mountятся в гостя.

До исполнения кода GSI процесс делает chroot/chdir, очищает supplementary groups,
устанавливает real/effective/saved UID/GID 65534 и явно обнуляет effective/
permitted/inheritable capabilities. Ambient caps очищаются. Parent-death signal
после UID change устанавливается заново, race проверяется owner pidfd.
Все унаследованные FD закрываются, кроме stdin EOF, stdout/stderr pipe и
служебного FD3 с CLOEXEC. Привилегированная metadata передаётся до exec; FD3
закрывается ядром при успешном exec, а guest stdout разбирается только как текст.

Затем no_new_privs и **новый default-deny allowlist** seccomp разрешают минимальные
file/memory/signal-handler syscalls для linker/mksh. Старый общий deny list из
диагностики не используется как sandbox. Запрещены fork/clone/clone3/vfork,
sockets/network, ptrace/remote-memory/BPF/perf, mount/setns, reboot, module,
privilege-changing syscalls, ioctl и остальные не перечисленные вызовы.
openat разрешён только для чтения; prctl — только anon-VMA naming, fcntl — только
GETFD/SETFD/GETFL, prlimit64 — только query self с NULL newlimit (обе половины
64-bit pointer проверены). ABI mismatch завершает процесс. Проверяются пять
безопасных отказов до exec.

Фиксированная команда:
```
/apex/com.android.runtime/bin/linker64 --library-path /apex/com.android.runtime/lib64/bionic:/system/lib64 /system/bin/sh -c "printf 'PD2425_GSI_SHELL_OK\n'"
```
Произвольная shell-команда от пользователя не принимается. Нет Android init,
servicemanager, zygote/system_server, HAL или дисплея. Это реальное исполнение
бинарников выбранного GSI, но не полноценный Android boot.

CPU limit 5 s, virtual address space 64 GiB, core dumps 0; fork/clone запрещены
фильтром. Это VA limit, не лимит физической RAM: Scudo резервирует несколько
GiB виртуального пространства уже при старте libc. RLIMIT_NPROC=0 не применяется,
поскольку после UID transition он может блокировать сам exec. Родитель ограничивает
execution фазу 20 секундами. Native общий deadline 300 s учитывает SHA 3 GiB,
APK ждёт до 360 s. Вывод ограничен 8 KiB и дренируется, чтобы pipe не завис.
Guardian завершает только свой ещё не reaped PID/pidfd. SIGCHLD временно default,
чтобы исключить recycling ID; нет kill по чужим PID или cgroup всего хоста.

После wait проверяются освобождение двух loop через GET_STATUS64 (ENXIO),
исходные parent root/mount/net identities и удаление собственного пустого temp
каталога. LOOP_CLR_FD/глобальное размонтирование и recursive rm не используются.
Если loop уже занят кем-то другим или cleanup не подтверждён, успех не выдаётся
и чужой loop не трогается. При аварийном прерывании возможен пустой собственный
каталог; перезагрузка допустима как recovery. Политика и root mounts хоста
не меняются намеренно; source/OTA/boot/vbmeta/system не прошиваются.

### Проверка и результат

Сохраните JSON прежней кнопкой root-отчёта. self_tests.gsi_preview содержит
preview_passed, точный image SHA, child stage/errno, UID/caps/filter proof, exit
status, ограниченный stdout и cleanup. Reviewer связывает его с snapshot по
boot ID/fingerprint и никогда не устанавливает runtime_ready или full boot.
В любом случае guest_boot_complete=false, launch_enabled=false.

Локально/CI проверены SHA vectors/file pins, ELF ABI, mock-loop read-only/autoclear
и отказ занятого/не-loop устройства, реальный child-only seccomp, default deny,
ограничения prctl/open/rlimit/fcntl, early host rejection и правила reviewer.
Android-сборка компилирует API; loop/mount/chroot/UID transition/SELinux/ARM64 exec
на PD2425 **ещё не проверены**. Если этап откажет, JSON покажет конкретный блокер.
Следующая работа после этого — private properties/APEX ART и guest services,
затем framework и только потом физическое оборудование с reboot recovery.


## Исправление обнаружения loop (0.1.12)

Отчёт владельца с 0.1.11 подтвердил SHA-256 выбранного raw GSI и создание
отдельных mount/network namespaces. Ошибка ENOENT получена на image_loop:
предыдущая версия не различала отсутствие loop-control и узла выбранного loop.
Код GSI ещё не выполнялся; ребёнок завершён/reaped, parent unchanged, временный
каталог удалён, cleanup_errno=0. Это не ошибка формата или подписи образа.

В 0.1.12 после LOOP_CTL_GET_FREE узел ожидается до 1 секунды. Если он не появился
или loop-control отсутствует, проверяются существующие loop0..loop1023 в
/dev/block и /dev. Каждый открытый FD должен быть block major 7 с точным minor.
Подключение только атомарным LOOP_CONFIGURE, READ_ONLY|AUTOCLEAR; EBUSY приводит
к следующему кандидату. Ошибки прав, типа узла и неподдержанного ioctl завершают
попытку, без обхода проверок. Loop-control также проверяется как char 10:237.
Новые device nodes не создаются, LOOP_CLR_FD и legacy SET_FD не используются.
Проверка освобождения применяет ту же проверку идентичности block FD.

В JSON добавлены loop_control_errno, loop_node_errno и loop_candidates, чтобы
различать отсутствие control, задержку/отсутствие block node и занятые кандидаты.
Они описывают путь поиска: errno может сохранять причину fallback даже при его
успехе; общий результат определяют preview_passed/child_errno/cleanup_errno.

Установите новый APK поверх прежнего: импортированный GSI сохраняется. Снова
нажмите «Запустить linker/sh из GSI» и сохраните root-report JSON. Прежний образ
перекачивать и импортировать повторно не требуется. Физическая проверка новой
ветки на устройстве пока не проведена; полный Android Start остаётся закрытым.
